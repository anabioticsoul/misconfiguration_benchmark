# MisconfigBench RQ2 / RQ3 初步实验与实现设计

日期：2026-10-14

状态：设计草案，供讨论；本文不表示对应功能已经实现。本次仅新增文档，不修改 agent、case 或评估脚本。

## 1. 研究目标与结论边界

建议将三个研究问题明确拆开：

| 研究问题 | 输入条件 | 主要测量对象 | 不应混淆的结论 |
|---|---|---|---|
| RQ1：能否正确理解并定位故障？ | 公开故障描述和故障环境 | 分类、组件/配置位置与根因诊断 | 修复成功不等于独立诊断正确 |
| RQ2：根因已经明确，能否有效修复？ | 公开描述、故障环境、经过审核的根因说明 | 从已知原因到可执行、持久化修复的能力 | 现有端到端 fixer 成功率不等于该能力 |
| RQ3：能否获取并使用正确证据？ | 可交互环境，或受控的证据包 | 有效证据获取、结论支持程度、对证据变化的响应 | 看过日志、解释流畅不等于真正使用证据 |

核心建议：RQ2 使用 oracle-guided repair；RQ3 使用在线证据采集审计，加离线受控证据实验。都先采用可检查的分项指标，不建立任意加权的“综合智能得分”。

## 3. 当前代码基础与缺口

目前已有：

- `agents/evaluator/fixer/run_case.py`：执行修复、导出配置补丁、调用隐藏评估脚本。
- `agents/evaluator/troubleshooter/`：输出分类与排序位置，按私有 metadata 评分。
- `agents/manager/openhands.py`：保存 `trajectory.jsonl`、模型输出和使用量。
- `agents/manager/batch.py`：筛选完整 instance，验证通过后顺序运行任务。
- `agents/evaluator/output.py`：按任务、provider、模型组织结果。

当前缺口：

1. Fixer prompt 只有公开任务，没有受控的根因提示。
2. 现有评估主要返回 exit code/stdout/stderr，不能稳定区分补丁契约、F2P、P2P 和安全检查失败。
3. 私有 `root_cause_detail` 多为简短标识，不宜直接当成高质量自然语言根因说明。
4. Troubleshooter 没有证据引用协议，也没有证据获取/支持性评分。
5. 诊断工具使用非特权 UID 和 `readOnlyHint`，但这不等于强制只读；仍可能写入可写目录，也可能无权读取关键日志。正式实验前应审计可观测性和副作用边界。

## 4. RQ2：给定根因的修复能力

### 4.1 先区分三种“标准答案”

| 名称 | 用途 | 是否提供给修复 agent |
|---|---|---|
| 诊断 oracle | 已审核的根因机制、组件/层、故障配置位置 | 仅在 oracle-root-cause 实验组提供 |
| 参考修复 | 一份能通过验收的已知 patch，用于环境校验与审计 | 不提供 |
| 行为 oracle | 隐藏 F2P、P2P、约束与安全测试 | 不提供测试源码、断言或预期修复值 |

“根因已知”不是“答案已知”。例如 CA136 可以提示“Nginx 到 PHP-FPM 的参数传递中缺少脚本路径，故障位于 PHP location 的 FastCGI 参数配置”，但不提供应添加的完整配置行。

对于某些简单拼写或缺失参数 case，根因提示天然会缩小到几乎唯一修复。应标注 `hint_solution_overlap` 并分层报告，而不是认为可以完全消除这种信息泄漏。

### 4.2 实验组

| 组别 | 提供的信息 | 目的 | 实施优先级 |
|---|---|---|---|
| E2E | 公开描述、故障环境 | 当前 fixer 基线 | 必做 |
| Oracle-Location | 在 E2E 基础上增加组件、文件、节或配置项位置 | 判断定位是否是主要瓶颈 | 第二阶段消融 |
| Oracle-Root-Cause | 在 E2E 基础上增加位置与根因机制，不给修复方案 | 直接回答 RQ2 | 必做 |
| Predicted-Diagnosis | 提供独立 troubleshooter 的诊断 | 衡量真实两阶段流水线及错误传播 | 后续扩展 |

每组从同一个故障镜像的全新容器启动，使用相同工具、公开描述、模型版本、预算与持久化策略。不能沿用 E2E 已经修改过的容器，也不能把之前运行的思考、修复、测试反馈传给 oracle 组。

不要仅挑选“RQ1 答对”的 case 再测 RQ2：这种条件子集往往更容易，会产生选择偏差。主实验应对预先确定的全部有效 case 提供人工审核根因。

### 4.3 根因说明格式与审核

建议在现有 `meta/metadata.json` 的 `private_oracle` 中扩展，而不是再建一套重复的 metadata 文件。下面是示意，不是已实现 schema：

```json
{
  "repair_context": {
    "component": "nginx-to-php-fpm",
    "layer": "inter-component request parameters",
    "location": {
      "path": "/etc/nginx/conf.d/default.conf",
      "section": "PHP location"
    },
    "cause": "The request does not convey the script filesystem path required by the backend.",
    "source_kind": "accepted_answer_adapted",
    "source_url": "<original source URL>",
    "review_status": "reviewed",
    "hint_solution_overlap": "moderate"
  }
}
```

根因说明只由 host 端按字段白名单读取和渲染，不能把整个 metadata 或 gold patch 放进 prompt、容器或 agent workspace。

来源区分：原问题接受答案、上游修复、官方文档、人工重建。LLM 可以辅助起草，但必须标记并由人工核对。原始案例与容器重建的版本差异、故障简化、修改过的需求也要记录。

建议至少两人独立审核：根因是否正确；是否足够明确；是否夹带修复指令/最终值；是否与公开任务冲突。记录分歧与裁决，不应把未知来源补写成“官方答案”。

### 4.4 多解、唯一解与执行验收

默认承认修复可能多解。参考 patch 仅证明存在一个已验证方案，不证明唯一性，也不是文本匹配目标。

建议接受条件：

```text
补丁可应用
AND 满足预先公开的修改/持久化约束
AND 所有 F2P 通过
AND 所有 P2P 通过
AND 显式安全不变量通过
```

如果公开需求确实要求固定值、路径或行为，可设置精确约束；否则不要因为与 gold patch 不同就拒绝。安全不变量与功能约束应对 agent 可知，具体隐藏测试实现保持私有。

代表性验收原则：

- 内存不足允许多个合理限额；应同时定义资源预算，不能仅以“无限制后能跑完”为成功。
- 回环地址允许行为等价的表达，但需要真实验证名称解析和监听行为；不默认把 `0.0.0.0` 视为安全等价解。
- 删除备份配置、改写备份内容、调整加载规则是否允许，必须由任务目标和修复范围决定，不能由参考 patch 的偶然形式决定。
- 重启/新容器回放是持久化检查；只在当前 shell 中生效不算配置修复，除非 case 明确允许操作型缓解。

不能穷举解空间时，论文应说明“通过测试的行为有效修复”，不要写成“证明修复完全正确”。新增隐藏测试需冻结版本，对所有模型结果一致重测，不可只针对某个模型补测试。

### 4.5 指标、失败归因与统计

主指标为 **Oracle-Root-Cause Repair Success Rate**：在根因提示组中，通过全部规定验收的独立运行比例。第一轮每 case 一次提交；不能把 agent 内部多次编辑当作多个独立样本。

同时报告：

- E2E success rate 与 oracle success rate 的配对差值。
- F2P 通过率、P2P 通过率、安全违规率、补丁有效率、每 case token 和时间。
- 按四大类、14 子类的样本数和结果；缺失子类写 N/A，不填零。
- API/基础设施失败、agent 超时、无有效补丁、契约失败、功能失败、回归失败分别计数。

差值只能说明“提供经过审核的诊断信息后表现改变”，不能严格拆成某个比例的“诊断错误贡献”；两组的行为和资源分配都会改变。

预先确定可用 case 集合，并对两组执行相同重试政策。报告全部计划运行的完成率，以及有效运行上的成功率；外部 API 故障不冒充模型修复错误，agent 自身预算耗尽计为任务失败。基础设施失效 case 需对配对实验对称处理并列出，不能按结果择优排除。

小规模试验先给出原始分子/分母。正式实验建议每 case/条件至少 3 个独立 rollout，报告均值及按 case 聚类的配对 bootstrap 区间；重采样单位为 case，不把同一 case 的重复尝试当成独立问题。需要显著性检验时预先定义比较，不在多个模型/子类中筛选显著结果。

### 4.6 现有 case 的前置修正

依据本仓库前期人工检查，正式 RQ2 前优先复核：

- CA108：导出 unified diff 与评估脚本读取 `diff --git` 的格式不兼容。
- CA130：公开描述允许跳过故障虚拟主机，而参考 patch 修正证书路径，允许修改范围是否支持公开目标需确认。
- CA147：公开任务倾向让 CLI 的 `html_errors=On` 生效，参考 patch 却改成 `Off`；先明确需求，不把冲突归咎于 agent。
- CA134：修改合法 `sql_mode` 的值，却被标为“Invalid option name”，需复核分类。

这些是待审核项，不在本文中自动更改标签或重判历史结果。

## 5. RQ3：证据获取与使用

### 5.1 将问题拆为两个可测子问题

**RQ3-A 获取：** 在信息不完整时，agent 是否主动拿到足以区分故障原因的观察？

**RQ3-B 使用：** 已经拿到证据后，诊断结论是否有支持，改变可用证据是否改变表现？

两者分开后才能区分“没有读日志”“读了日志但误解”“环境根本不允许读日志”。不要求披露或评估模型内部 chain-of-thought，仅评估可观察的命令、返回内容、最终结论和受控实验结果。

### 5.2 私有证据标准：标注事实，不标唯一命令路线

每个 case 先人工定义少量诊断相关事实，并区分：故障现象、机制相关事实、排除其他解释的事实。不同事实可以有多个等价获取方式；不同充分证据集合也可以得到同一个诊断。

以 CA151 为例：

| 证据事实 | 可接受的观察举例 | 不能单独作为该事实的证明 |
|---|---|---|
| 实际监听仅在回环接口 | 套接字监听信息、受控连通性观察结合地址信息 | 仅看到“连接失败” |
| 存在相互冲突的配置值 | 两个配置文件内容或完整解析后的配置报告 | 仅列出配置文件名 |
| 后加载配置造成实际覆盖 | 加载顺序与有效配置值，或其他经过审核的等价证据组合 | 仅凭文件名猜测加载优先级 |

“执行 `cat`”不等于证据已获得。输出需成功返回、包含相关内容、确实进入 agent 可见上下文；未读取的日志文件和被截断的关键行不算可见证据。

新增 private `evidence_oracle` 字段，保存事实 ID、事实描述、等价证据来源/模式、适用子类、充分集合和审核信息。私有事实 ID 不发给 agent；agent 只引用公开的 observation ID。

### 5.3 按类别设计观察重点

| 类型 | 代表子类 | 通常需要的证据 |
|---|---|---|
| CA：约束违反 | 语法、无效名称、位置错误、重复项、组件内/跨组件约束 | 解析错误、加载文件与节、配置顺序、版本支持范围、有效配置和组件两端状态 |
| CB：资源不可用 | 标识不匹配、竞争、权限、硬件限制 | 资源实际存在性、解析结果、占用者、运行 UID/ACL、资源使用量与限制 |
| CC：组件集成 | 不兼容、缺失 | 已安装版本、依赖/模块列表、加载失败与接口兼容信息 |
| CD：语义误解 | 名称歧义、值与需求不符 | 文档或运行语义、目标工作负载、实际行为与期望行为的可复现差异 |

这是标注指导，不是统一必读清单。语法错误可能一条解析错误就足够，不应因为没有读取版本或依赖而扣分。真实新证据不在预定义集合内时，应进入盲审补充流程并统一回评，不能直接判无效。

### 5.4 最小协议改动

复用现有 `trajectory.jsonl`，在诊断工具返回结果中加入 host 生成的稳定 observation ID，保存命令、退出码、实际展示给模型的输出，以及截断标记。SDK 事件 ID 与 observation ID 建立映射，不仅在离线日志里编号。

在当前诊断 JSON 上增加可选字段，不破坏 RQ1 的分类与定位输出：

```json
{
  "classification": {"type_id": "CA", "subtype_id": "CA-3"},
  "ranked_locations": [],
  "claims": [
    {
      "kind": "root_cause",
      "text": "A later-loaded configuration overrides the intended listening address.",
      "evidence_refs": ["obs-0003", "obs-0007"]
    }
  ]
}
```

核心 claim 类型限定为 symptom、root_cause、localization；不因多写解释或多引用获得额外奖励。引用必须指向提交结论之前的、该运行中真实存在的观察。可增加简短摘录用于审计，但需检查其是否在原观察中，不能相信模型自行生成的引文。

### 5.5 在线获取指标与证据支持指标

第一版只做四项：

| 指标 | 建议定义 | 边界 |
|---|---|---|
| 充分证据获取率 | 获得至少一套经审核充分事实集合的运行占比 | 证据标准不完整时只能称“已标注充分集合覆盖率” |
| 到首套充分证据的成本 | 首次取得充分集合前的工具调用数、时间、输入/输出 token | 未取得者报告未达到比例，不从均值中悄悄删除 |
| 引用有效率 | 指向本次真实可见观察的引用数 / 全部引用数 | 空引用报告 N/A 和缺失数，不算满分；有效不等于支持结论 |
| 核心结论支持率 | 获得观察支持的必要结论槽位 / 全部必要槽位 | 缺少必要结论也记缺失；固定槽位避免少说少错、多说刷分 |

“支持结论”与“结论正确”分别报告：错误结论可能引用了真实但被误读的证据；正确结论也可能缺少可追溯依据。RQ1 的分类/定位指标仍负责结果正确性。

支持性判定优先用结构化检查，复杂语义先人工标注。可让 LLM 辅助预标，但不能让它既生成 oracle 又独立决定最终分数。先对跨类别样本双人盲审，记录一致率或 Cohen's kappa，并报告分歧裁决；若引入 judge，记录模型版本、prompt 和对人工标签的误差。

“调用工具越多越好”“日志词出现次数越高越好”均不作为质量指标。重复检查可能是合理验证，不能仅凭命令相同就判无效。

### 5.6 受控证据实验：优先离线重放，不拦截任意 shell

先用只读诊断运行收集 observation，构建固定证据包。对同一个 case、同一个模型进行新的无工具诊断调用；不传原 agent 的诊断、思考、修复或验证结果。使用同一个最终 JSON 协议与同一版本 RQ1 评分。

| 条件 | 提供内容 | 解释目的 |
|---|---|---|
| Description-Only | 相同公开描述，无工具观察 | 测量公开描述/先验已能解决多少问题 |
| Full-Evidence | 描述与冻结的完整证据包 | 受控参考条件 |
| Key-Evidence-Only | 描述与经审核的充分证据集合 | 检查这些证据在行为上是否足够 |
| Key-Evidence-Removed | 描述与移除关键事实后的证据包 | 检查缺失关键证据是否影响诊断 |
| Matched-Control | 移除相近 token 数的非关键观察 | 控制上下文长度变化的影响 |

移除的是关键事实的所有已知重复呈现，而不是只删除一个日志文件的某一行。若公开描述已经泄露同一事实，保持描述不变，但标注为不适合“必要性”结论的样本。证据选择需在查看待比较模型结果前冻结。

建议差值：

```text
关键证据移除影响 = Accuracy(Full) - Accuracy(Key-Removed)
充分证据保留损失 = Accuracy(Full) - Accuracy(Key-Only)
描述基线增益     = Accuracy(Full) - Accuracy(Description-Only)
```

同时对比 Matched-Control，避免把所有下降都归因于证据内容。差值允许为负，保留原始结果，不裁剪。Accuracy 使用预先选定的 Joint@1 或其他固定诊断指标，并同时提供分类、定位分项。

这借鉴 ERASER 的干预思想，但属于本项目的行为实验；它检验模型对提供信息的敏感性，不能证明原在线 agent 在内部采用了某条推理链。在线过程与离线重放的分布不同，结果必须分表报告。

第一版证据包可以来自人工审核的标准诊断流程，以公平比较“使用能力”。模型自身收集的证据包用于分析“获取后能否利用”，但不同模型的自采证据不能直接当作相同输入条件比较。

### 5.7 运行隔离与观测公平性

- 工具层保证私有 metadata、参考 patch、隐藏测试不在可读范围；不是只依靠 prompt 禁止读取。
- 为非特权诊断提供经过脱敏的必要日志/有效配置查询，避免把权限障碍误判成不会诊断。
- 对写文件、服务变更或会修复状态的命令进行约束/审计；不能声称 `readOnlyHint` 已强制只读。
- 拒绝只用正则拦截 `cat`/`grep` 的“无日志实验”：模型可以通过 Python、其他命令重新获取相同证据。
- 若后续研究在线证据通道消融，应采用明确的只读诊断 API 或隔离后的遥测视图，并审计泄漏和语义一致性；不作为第一版必做。

## 6. 建议的最小实现结构

遵循现有分层，不新增一个复杂的“评审 agent 系统”：

```text
agents/evaluator/
  fixer/
    prompts.py             # 扩展：E2E/location/root-cause 输入模式
    run_case.py            # 扩展：实验条件、分项验收输出
  troubleshooter/
    openhands_tools.py     # 扩展：可见 observation ID
    scoring.py             # 保留 RQ1 评分，不混入证据总分
    evidence.py            # 新增：证据映射和支持性审计结果
    evidence_replay.py     # 后续：冻结证据包的受控诊断
agents/manager/
  openhands.py             # 复用事件记录与成本统计
  evaluation.py            # 扩展：结构化 F2P/P2P/安全状态
  batch.py                 # 复用遍历和进度，不放角色专属评分
prompts/
  misconfig_repair_oracle.j2
  misconfig_diagnosis.j2    # 可选证据引用输出
```

CLI 可增加 `--repair-context none|location|root_cause`；默认 `none` 保留当前行为。旧 case 缺少审核根因时，oracle 模式应明确跳过并报告，不能静默降级成 E2E。

结果建议增加 `protocol_version`、`dataset_revision`、`image_digest`、`prompt_hash`、实验条件及预算。现有按 provider/model 分组还不够：同模型不同 repair context 或 evidence condition 必须分组，且能追溯 case/harness 版本。

验收 JSON 示例：

```json
{
  "repair_context": "root_cause",
  "evaluation": {
    "patch_apply": "pass",
    "policy": "pass",
    "f2p": "pass",
    "p2p": "pass",
    "safety": "not_evaluated",
    "functional_success": true,
    "safe_success": null
  }
}
```

未执行安全测试不能填 `pass`；旧脚本只有整体退出码时，分项状态应为 unknown/not_evaluated，不能根据没有报错推断全部通过。升级 case harness 时需保留原 stdout/stderr 和兼容路径。

## 7. 与安全 Discussion 的关系

安全作为功能修复的独立约束与分析维度，避免“返回 200 就算成功”。建议至少考虑：无效密码仍被拒绝、未扩大网络暴露、未全局放宽权限、未绕过 TLS 校验、未移除需要的业务路径。

这些不是所有 case 的统一必测项：按公开威胁模型与原需求选择适用检查。测试本来就使用关闭 TLS 验证等简化配置时，必须说明该环境不能证明生产安全性。

分开报告：计划/验证/评估的数量、功能通过数、安全检查覆盖数、安全违规数、安全通过数。在有安全测试的 case 中，可报告功能成功但安全失败比例；不能把未测试安全的样本称为安全成功。

RQ3 还可做描述性案例分析：是否在首次修改前检查了关键证据，是否在修复后检查负例。与安全成功的相关性不自动构成因果结论。

## 8. 分阶段实施与预期产出

### 阶段 A：先把 RQ2 做成可解释实验

1. 审核已发现的验收/描述冲突，冻结第一版有效 case 清单。
2. 为试验集补充来源可追溯的根因说明，核对泄漏边界。
3. 实现 E2E 与 Oracle-Root-Cause 两组，分项记录失败阶段。
4. 对相同 case 和模型配对运行，产出成功率、类别分布和成本表。

验收标准：模型只接收白名单根因字段；gold patch/隐藏测试不泄漏；两组使用相同故障基线；失败类别可区分；不会因缺少 oracle 而混入 E2E。

### 阶段 B：先回答 RQ3 的可观察部分

1. 为一个覆盖四大类的小规模集合标注关键事实和充分证据集合。
2. 增加 observation ID、结论引用、轨迹导出和人工审核表。
3. 报告获取率、获取成本、引用有效率、核心结论支持率，以及 RQ1 正确性。
4. 固定证据包后再实现保留/移除实验，不在第一轮重构 shell 沙箱。

验收标准：引用能定位到模型实际见到的原始输出；可区分不可获取、未获取、误读和无依据结论；离线干预不夹带原始答案或 agent 思考；私有事实清单未暴露给 agent。

### 首轮规模建议

先人工挑选 12–16 个审核通过的 case，覆盖四大类及尽量不同子类；这是工程与协议试验，不用于宣称全类别性能。先跑 1 个模型/每条件 1 次检查流程，再增加模型和重复次数。

全量正式实验使用冻结的完整有效集合，并披露未覆盖子类。只有版本/预算固定后，才扩大到多个模型；记录运行日期、完整模型别名及第三方 API provider，不能仅写“Claude/Gemini/DeepSeek”。

## 9. 建议论文表格

**RQ2 主表**：模型、有效/计划运行数、E2E 成功率、Oracle-Root-Cause 成功率、配对差值及区间、功能回归率、安全覆盖与违规率、平均 token/耗时。

**RQ2 分类表**：四大类/子类、case 数、两组成功数/运行数、主要失败阶段。不要对零样本类别给分。

**RQ3 在线表**：模型、充分证据获取率、未达到比例、获取成本、引用有效率、核心结论支持率、Joint@1。

**RQ3 干预表**：同一模型在 Description-Only、Full、Key-Only、Key-Removed、Matched-Control 下的诊断准确率与配对差值；明示这是无工具证据重放。

**Discussion 表**：功能成功且安全通过、功能成功但安全失败、功能失败、安全未评估；配合少量有真实轨迹和测试证据的案例，不把所有失败归为模型能力不足。

## 10. 本轮需要确认的设计选择

1. RQ2 是否采用“根因 + 位置，不给修复行”作为主协议？建议是。
2. 是否将不同合法修复交给动态测试和公开约束判断，而不比较 gold patch 文本？建议是。
3. RQ3 是否先做证据引用和人工审核，再做离线干预，暂缓在线 shell 通道消融？建议是。
4. 是否先审核小规模跨类别试验集再扩大运行，避免消耗大量 token 后才发现 oracle 有问题？建议是。

最终可以回答的不是“agent 会不会真正思考”，而是：在可复现任务中，提供根因是否改善修复；agent 是否获得足够证据、给出有依据的诊断，以及诊断表现如何随可用证据变化。
